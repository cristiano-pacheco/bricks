# Maintain the Bricks skill

Follow this workflow when changing a public API, configuration field, default, supported scenario, or lifecycle behavior. Consumer instructions belong in `skills/bricks/`. Implementation evidence belongs in the affected Obsidian ticket, following the [tracker workflow](issue-tracker.md).

1. Identify the changed contract from the current implementation and its callers. Record the affected packages, exported usage paths, scenarios, and lifecycle or error behavior in the ticket. Include unreleased behavior. This step is complete when each changed contract has an owning package guide or branch under `skills/bricks/references/`.
2. Update that guide's numbered setup, inline Go, alternatives, field explanations, and caveats together. Keep required imports, types, providers, interface bindings, groups, error handling, and cleanup with the setup. For configurable packages, update minimal and full-field YAML and each meaningful scenario file under `skills/bricks/examples/`. Update locale JSON and migration SQL when affected. Record Go-only inputs separately. This step is complete when the guide and retained assets describe the same contract. Keep `examples/` for configuration and supporting data; do not recreate standalone Go programs or tests there.
3. Update affected composition recipes and conditional pointers. Change `skills/bricks/SKILL.md` only when task selection or a destination changes. Update project, glossary, and agent-facing links when affected. Keep package explanations in their owning guide rather than repeating them in indexes. This step is complete when each new or moved capability has a task-conditioned route and no instruction requires a removed file.
4. Verify the changed consumer path when execution is authorized. Copy the inline code and required assets into a temporary consumer application. Compile complete setups and validate Fx graphs separately from startup and runtime behavior. Load minimal, full-field, and scenario YAML through the real loader. Exercise the relevant public operation, expected errors, and shutdown. Use controlled services where needed and actual listening HTTP interfaces for E2E proof. Follow the [command map](commands.md) and current repository command definitions for applicable checks. For source-discovery changes, exercise cache, replacement, workspace, vendor, and unavailable-source cases without downloads or dependency edits. This step is complete only with actual results, or an explicit waived or not-run disposition. A waived check is not a pass.
5. Follow each changed recommended path using only the distributed skill. Record copied files, commands, results, and a comparison with the existing package README. For routing changes, record the task, actual selected references, unrelated exclusions, clarification, and deduplication behavior. Static links are not routing proof. Estimate context sizes with a stated method and investigate overruns without hiding setup. This step is complete when the ticket distinguishes content inspection from consumer execution and records remaining gaps.
6. Decide whether README removal is safe. Keep every affected package README until useful replacement coverage, reader clarity, configuration loading, compilation, Fx graphs, relevant runtime behavior, and inbound-link updates have evidence. An execution waiver for a documentation task does not authorize README deletion. Preserve the root overview. This step is complete with either supported removal and updated inbound links, or an explicit preservation decision and its blockers.
7. Finish the ticket with the affected guide, recipe, router, inline-code, and asset paths, verification results, waivers, and commit. Record each check as passed, failed, or not run with its reason. Keep historical evidence when scope changes. Propose library fixes separately and obtain approval before implementing them. This step is complete when every criterion is implemented or explicitly waived, unresolved blockers remain visible, and the saved tracker status matches that disposition.

The current documentation work waived reviews, lint, tests, compilation, routing evaluation, YAML execution, and runtime walkthroughs. Those waivers are recorded in implementation tickets and leave the README-removal gates unverified. This workflow describes future maintenance; it does not claim those checks ran.
